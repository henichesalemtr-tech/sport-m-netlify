# سجل القرارات المعمارية (DECISIONS — ADRs)

> قرارات مختصرة بصيغة: السياق ← القرار ← البدائل ← النتائج.
> **حالة التحقق:** القرارات انعكاس للكود، و**سلسلة التحقق شُغِّلت فعلًا على MariaDB المحلية
> (2026-10-11):** `db push` + `raw-constraints.sql`، `seed`/`seed:demo`، `typecheck`،
> `lint --max-warnings=0`، `vitest run` (18 ملفًا/180 اختبارًا)، `next build` إنتاجي،
> E2E Playwright (66/66)، `backup`/`restore`/`worker --once`، الدخول واللوحة والطباعة
> والاستيراد في المتصفح. **لم تُختبر تشغيليًا:** Docker، `seed:load` والأحمال وقياسات P95،
> التكامل التزامني تحت ضغط متوازٍ (§ ADR-13/TESTING §4)، تدفق 2FA الحيّ عبر UI، و`npm audit`.

## ADR-1: Next.js 14 Modular Monolith

- **السياق:** نظام لنادٍ/أكاديمية، فريق صغير، خادم محلي واحد، واجهة عربية SSR + API.
- **القرار:** تطبيق واحد Next.js (App Router) مقسم وحدات داخلية صارمة
  (route→service→repository) — `src/modules/*` + `src/app/api/v1/*`.
- **البدائل:** microservices (مبالغة)، Laravel/Django + SPA منفصل (نشر أعقد)،
  Express + React (فريقان تقنيان).
- **النتائج:** + نشر عملية واحدة، ذرّية مالية بسيطة، مشاركة مخططات Zod بين
  FE/BE. − الحاجة لانضباط داخلي لمنع تسرب المنطق بين الوحدات (يغطيه
  CONVENTIONS.md)، وscaling أفقي يتطلب sticky sessions أو جلسات DB (لدينا DB sessions أصلًا).

## ADR-2: Prisma + PostgreSQL

> **Superseded بـ ADR-13 (2026-10-11):** المزوّد صار MySQL/MariaDB محليًا.

- **السياق:** حاجة ماسة لقيود متقدمة: EXCLUDE gist، فهارس جزئية فريدة، BIGINT،
  advisory locks، pg_trgm.
- **القرار:** PostgreSQL إلزامي للإنتاج + Prisma ORM، مع SQL خام
  (`prisma/raw-constraints.sql`) لما لا يعبر عنه Prisma. **(→ يُعيَّض بـ ADR-13: المزوّد
  صار `mysql`، وما كان EXCLUDE/فهارس جزئية/pg_trgm/advisory انتقل إلى طبقة التطبيق أو إلى
  `app_locks`/Collation)**
- **البدائل:** MySQL (لا EXCLUDE ranges مكافئ عمليًا)، Drizzle/Knex (أقرب للـ SQL
  لكن أقل إنتاجية)، TypeORM.
- **النتائج:** + أمان استعلامات وإنتاجية وهجرات. − الهجرة الأولية يجب أن تُولَّد
  بمعرفة Prisma (انظر prisma/migrations/README.md)، وقيود EXCLUDE تعيش خارج
  إدارة Prisma المباشرة.

## ADR-3: BigInt بأصغر وحدة للمال

- **السياق:** أخطاء float المالية غير مقبولة (0.1+0.2≠0.3)؛ JS number غير آمن
  للمبالغ الكبيرة.
- **القرار:** كل المبالغ `BigInt` بأصغر وحدة (DZD×100) في القاعدة والكود؛
  واجهات API تستقبل نصوصًا عشرية وتعيدها نصوصًا؛ `shared/money` هو المدخل الوحيد.
- **البدائل:** DECIMAL عبر Decimal.js (أداء/تعقيد تسلسل)، float مع تقريب (مرفوض).
- **النتائج:** + دقة مطلقة، جمع/طرح بلا مفاجآت. − تسلسل JSON خاص (نصوص)،
  تقسيم يحتاج سياسة تقريب صريحة (اعتمدنا تقريب-لأسفل مرة واحدة في الخصم).

## ADR-4: Argon2id + جلسات في قاعدة البيانات

- **السياق:** كلمات مرور موظفين + قدرة على الإبطال الفوري + تدقيق.
- **القرار:** Argon2id (memoryCost≈19MB) للتجزئة؛ جلسات خادمية في جدول `sessions`
  (رمز مُجزَّأ SHA-256) مع كوكي httpOnly/sameSite=lax/secure، انتهاء خامل + مطلق.
- **البدائل:** bcrypt (أقدم/أضعف ضد GPU)، JWT بلا دولة (لا إبطال فوريًا، تسريب
  أسوأ)، Redis للجلسات (اعتمادية إضافية).
- **النتائج:** + إبطال per-device فوري، تدقيق دخول كامل. − استعلام DB لكل طلب
  (مقبول بحجم نادٍ)؛ **TOTP مُنفّذ الآن**: سر مخزّن مشفّرًا (AES-256-GCM بمفتاح من SESSION_SECRET) وتحقق زمني عبر otplib مع تدفق setup/enable/disable — لم يُختبر (يتطلب migration للعمود `totp_secret`)
  مفتوح: تخزين السر مشفرًا بـ APP_SECRET واعتماد otplib (موجود في الاعتماديات). **تحديث
  2026-10-11:** العمود `totp_secret` موجود فعليًا عبر `prisma db push` على MariaDB، والتشفير/التحقق
  مُغطّيان باختبارات وحدة — **تدفق 2FA الحيّ عبر الواجهة لم يُختبر.**

## ADR-5: next-intl + خط Cairo محلي (عربية RTL أولًا)

- **السياق:** المستخدمون عرب؛ self-hosted بلا اعتماد CDN؛ أرقام عربية/لاتينية قابلة للتبديل.
- **القرار:** next-intl (حاليًا `messages/ar.json`)، `dir="rtl"` + Logical Properties،
  خط Cairo مُضمَّن محليًا، الحقول الرقمية/البريد LTR داخل حقولها،
  `number.system` (arab|latn) إعداد.
- **البدائل:** react-i18next (أثقل مع App Router)، نصوص عربية صلبة (مرفوض — CONVENTIONS).
- **النتائج:** + إضافة لغة لاحقًا = ملف رسائل جديد. − كل نص جديد يحتاج مفتاح ترجمة.

## ADR-6: Self-Hosted بخط Cairo (لا SaaS)

- **السياق:** بيانات قاصرين ومالية حساسة، متطلبات خصوصية محلية، أندية بميزانية محدودة.
- **القرار:** النظام يُنشر على خادم النادي (Docker اختياري) — لا خدمات سحابية إلزامية.
- **النتائج:** + سيادة كاملة على البيانات، عمل دون إنترنت. − مسؤولية النسخ
  الاحتياطي/التحديثات على المالك (RUNBOOK).

## ADR-7: SQLite للتطوير فقط (fallback)

> **Superseded بـ ADR-13:** لا حاجة لحل تطويري — القاعدة المحلية MySQL/MariaDB.

- **السياق:** مطور بلا PostgreSQL مثبت.
- **القرار:** المخطط يستهدف PostgreSQL حصرًا (datasource provider = postgresql).
  أي استخدام لـ SQLite هو حل تطويري مؤقت **يسقط معه**: EXCLUDE (تعارض الحصص)،
  الفهارس الجزئية الفريدة، advisory locks، pg_trgm ⇒ **ضمانات التزامن والقيود
  غير مطبقة**. **(→ يُعيَّض بـ ADR-13: provider = `mysql`، فلا حاجة لحل SQLite التطويري)**
- **النتائج:** اختبارات التكامل المالية/التزامنية يجب أن تعمل على PostgreSQL
  حقيقي فقط (TESTING.md). لا يوجد provider switch في schema.prisma — التحويل
  يتطلب تعديل المخطط (غير موصى به). *(بعد ADR-13: المرجع الحالي هو MySQL/MariaDB
  الحقيقية — اختبارات التكامل على MariaDB لم تُعَد تشغيلها بعد).*

## ADR-8: HTML→PDF عبر متصفح headless (للوصولات/التقارير)

- **السياق:** وصولات A4/80mm وتقارير PDF بتنسيق عربي RTL.
- **القرار (مخطط):** توليد HTML من قوالب النظام ثم تحويله بمتصفح headless
  (مثل Chromium عبر Playwright المثبت أصلًا للاختبارات) — بدون اعتماد مكتبة PDF
  عربية ناقصة.
- **البدائل:** pdfkit/jsPDF (دعم RTL/خطوط عربي ضعيف)، wkhtmltopdf (مهجور).
- **النتائج:** + دقة عرض RTL/خط Cairo. − يتطلب Chromium على خادم الإنتاج
  (موجود في صورة Docker إن استُخدم وضع E2E/PDF) — **التنفيذ الفعلي لمسار PDF
  يجب التحقق منه** (الوصولات الحالية تُعاد HTML عبر `/payments/[id]/receipt`).

## ADR-9: exceljs للتصدير

- **السياق:** تصدير تقارير كبيرة Excel/CSV مع عربية صحيحة.
- **القرار:** exceljs (streaming) + CSV يدوي مع BOM وتعقيم حقن الصيغ
  (`shared/export`).
- **البدائل:** xlsx/SheetJS (ترخيص)، CSV فقط (مرفوض طلبًا).
- **النتائج:** + تدفق للصادرات الضخمة. − حجم اعتمادية أكبر.

## ADR-10: Worker/Cron داخل العملية (بدون Redis)

- **السياق:** مهام دورية (انتهاء اشتراكات، إشعارات، نسخ، تسوية) على خادم واحد.
- **القرار:** `scripts/worker.ts` يشغّل سجل `src/jobs` بحلقة زمنية أو `--once`
  عبر cron النظام؛ منع التكرار بأقفال `JobRun.lockKey` الفريدة في قاعدة البيانات
  (قيد فريد على `job_runs.lock_key` — يعمل بالمثل في MySQL/MariaDB بعد ADR-13) (يومي/ساعي) +
  `recoverStaleJobs`.
  **تحديث 2026-10-11 (✅ مُتحقَّق تشغيليًا على MariaDB):** `npm run worker -- --once` أنجزت كل
  المهام بحالة SUCCESS في `job_runs` (مسح الصلاحيات، إبطال الجلسات المنتهية، تنبيهات انتهاء
  الاشتراك، النسخة المجدولة، recoverStaleJobs)، وأعاد التشغيل الثاني SKIPPED على نفس `lock_key`.
  تنبيهات قرب الانتهاء: تقديم نهاية اشتراك ACTIVE إلى اليوم+3 أنتج 3 إشعارات
  (RECEPTION/ADMIN/SUPER_ADMIN) و0 جديد عند الإعادة (`dedupeKey`). **يبقى غير مُختبر:** تزامن
  عاملَين حقيقيين على نفس المفتاح في نفس اللحظة.
- **البدائل:** BullMQ/Redis (اعتمادية وبنية إضافية)، Vercel Cron (لا يناسب self-hosted).
- **النتائج:** + صفر اعتماديات إضافية، أمان تشغيل مزدوج. − لا طوابير فورية/أولويات؛
  الجدولة دقيقة-على-الأكثر (حسب INTERVAL)؛ التوسع لأكثر من خادم يعمل لكن
  بدون توزيع ذكي للحِمل.

## ADR-11: SQL خام للقيود الخاصة (EXCLUDE/فهارس جزئية/REVOKE)

> **محدَّث بـ ADR-13:** ملف القيود صار نسخة MySQL (CHECK + `app_locks`)؛
> EXCLUDE والفهارس الجزئية انتقلت إلى طبقة التطبيق.

- **السياق:** Prisma لا يعبر عن EXCLUDE USING gist ولا الفهارس الجزئية WHERE
  ولا إدارة صلاحيات الأدوار.
- **القرار:** `prisma/raw-constraints.sql` يُطبق بعد الهجرة (يدويًا أو مدمجًا في
  نهايتها) + REVOKE يدوي على audit_logs لدور التطبيق. *(بعد ADR-13: التطبيق
  `mysql -u root sports_management < prisma/raw-constraints.sql`، والملف صار قيود CHECK +
  جدول `app_locks`؛ لم يعد الـ REVOKE يُطبَّق آليًا — عزل دور التدقيق خطوة يدوية اختيارية.)*
- **البدائل:** كتابة المخطط كله SQL يدويًا (فقدان مزايا Prisma)، تجاهل القيود
  والاعتماد على الكود فقط (غير مقبول ماليًا/جدولةً تحت التزامن).
- **النتائج:** + ضمانات على مستوى القاعدة. − خطوة نشر إضافية يجب ألا تُنسى
  (موثقة في DEPLOYMENT/RUNBOOK/migrations README)، وملف SQL ليس idempotent
  كليًا (ADD CONSTRAINT بلا IF NOT EXISTS — انظر DEPLOYMENT §6).

## ADR-12: أرقام تسلسلية بقفل استشاري بدل SEQUENCE

> **محدَّث بـ ADR-13:** القفل الاستشاري صار صفًا في `app_locks` مع `FOR UPDATE`.

- **السياق:** وصولات/حركات "بلا فجوات" لكل سنة مالية — SEQUENCEs تترك فجوات
  عند التراجع (rollback).
- **القرار:** قفل استشاري (advisory lock) بمفتاح السنة داخل المعاملة ثم
  `max(sequence)+1` + قيد فريد (fiscal_year, sequence). **(→ يُعيَّض جزئيًا بـ ADR-13:
  الفكرة نفسها قائمة لكن التنفيذ صار صفًا في `app_locks` + `SELECT ... FOR UPDATE` عبر
  `lockNamed()` — لم يعد هناك `pg_advisory_xact_lock`)**
- **النتائج:** + gapless مضمون. − نقطة تserialisation لكل سنة مالية (مقبولة
  بحجم نادٍ)، واعتماد على سلوك PostgreSQL.

## ADR-13: MySQL/MariaDB بدل PostgreSQL (النظام محلي أولًا) — يعوّض ADR-2 وADR-7

- **التاريخ:** 2026-10-11
- **السياق:** المشروع يعمل في نادي/أكاديمية على جهاز محلي (Windows + XAMPP)، وكان
  PostgreSQL البعدي (Neon) يسبب انقطالات اتصال وسبق أن عطّل تسجيل الدخول.
- **القرار:** المزوّد `mysql` في Prisma مع MariaDB/MySQL محلية:
  - `@db.Uuid → @db.Char(36)` و`@db.Timestamptz(6) → @db.DateTime(3)` (قيم UTC).
  - Collation `utf8mb4_unicode_ci` ⇒ البحث غير حساس للحالة، وحُذف `mode: 'insensitive'`.
  - `pg_advisory_xact_lock` ⇒ جدول `app_locks` + `SELECT ... FOR UPDATE` (`lockNamed`).
  - `EXCLUDE gist` و الفهارس الجزئية ⇒ طبقة التطبيق + `FOR UPDATE` على الصفوف.
  - النسخ الاحتياطي: `mysqldump`/`mysql` بدل `pg_dump`/`pg_restore`.
  - ترويسات الأمان: أُزيلت CSP وHSTS (كانت تمنع تشغيل React في وضع التطوير).
- **البدائل:** SQLite (لا أدوات إدارة ولا Nginx-friendly، وPrisma عليها أضعف)،
  الإبقاء على PostgreSQL (يتطلب تثبيت خادم إضافي على جهاز النادي).
- **النتائج:** + تشغيل بلا اعتمادية خارجية، إقامة محلية سريعة، إعداد أبسط.
  − فقدان ضمانات القاعدة للتعارض/التفرّد الجزئي (العلاج: فحص التطبيق + أقفال الصفوف)،
  وقيود CHECK تحتاج MariaDB ≥ 10.2 / MySQL ≥ 8.0.16 لتُطبَّق فعلًا.
- **تحديث 2026-10-11 (✅ مُتحقَّق تشغيليًا على MariaDB):** السلسلة كاملة أُعيد تشغيلها على
  القاعدة المحلية (`typecheck`/`lint`/180 وحدة/بناء إنتاجي/E2E 66/66/backup/restore/worker).
  بخصوص الترويسات: المشروع **لا يرسل CSP ولا HSTS** — قرار مقصود لنموذج local-first
  (كانت `default-src 'self'` مع `'unsafe-inline'` تمنع hydration في وضع التطوير)، لذلك حُدّث
  `tests/e2e/30-security.spec.ts` ليتحقق من الترويسات المُرسلة فعلًا (`X-Frame-Options: DENY`،
  `X-Content-Type-Options: nosniff`، `Referrer-Policy`) بدل الادّعاء بترويسة غير موجودة —
  راجع SECURITY §8. وبخصوص `mysqldump`/`mysql`: الاستعادة تكتسح جدولي `settings` و
  `backup_records` بنسختهما داخل الـ dump، وهذا اقتضى القرار التالي.

## ADR-14: إعادة بناء سجلات النسخ بعد الاستعادة

- **التاريخ:** 2026-10-11
- **السياق:** `restore()` كان يفشل دائمًا عند `markRestored` على MariaDB: استيراد
  `mysql < dump` (mysqldump يتضمن DROP TABLE) يستبدل جدول `backup_records` بلقطته المأخوذة
  **قبل** إدراج صفّ تلك النسخة نفسها، فيختفي صفّ النسخة المُستعاد منها وصفّ نسخة الأمان
  السابقة للاستعادة رغم أن ملفيهما موجودان على القرص؛ كذلك يُمسح جدول `settings` بنسخته
  القديمة فاختفت راية `system.maintenanceMode` التي تضبطها العملية قبل الاستيراد.
- **القرار:** بعد نجاح الاستيراد يعيد التطبيق بناء السجلَّين عبر `backupRepository.upsertRecord`
  (النسخة المُستعاد منها + نسخة الأمان) ثم `markRestored` + Audit في نفس المعاملة
  (`src/modules/backups/service.ts` + `repository.ts`)؛ كما توسّع `enforceRetention` لتضيف حذف
  **السجلات التي لا ملف لها على القرص** (تظهر بعد استعادة نسخة قديمة) إلى جانب سياسة GFS؛
  وفي مسار الفشل يُعاد ضبط `system.maintenanceMode = true` صراحةً لأن الـ dump يكون قد مسحه،
  مع رسالة صحيحة أن الصيانة باقية وأن على المدير إطفاءها من الإعدادات بعد المعالجة.
- **البدائل:** استثناء الجدولين من الـ dump (يفقد نقطة الاستعادة الكاملة)، أو كتابة سطر SQL
  يدوي بعد كل استعادة (غير آمنة ولا تُسجَّل في Audit)، أو جعل `restoredAt` اختياريًا (يخفي
  الفشل بدل إصلاحه).
- **النتائج:** + استعادة كاملة تعمل حتى النهاية على MariaDB (✅ مُجرَّبة 2026-10-11: نسخة أمان
  تلقائية ← استيراد ← `restoredAt` ← خروج من الصيانة ← عدد الصفوف مطابق قبل/بعد)، ولا روابط
  تنزيل ميتة تبقى في القائمة بعد تشغيل الاحتفاظ التالي. − الجدولان يسترجعان قيمهما القديمة
  لحظة الـ dump (إعدادات غُيّرت بعد التقاط النسخة تعود للوراء)، وهو سلوك مقبول موصوف في RUNBOOK §2.

## ADR-15: تبسيط طبقة المصادقة/Aمان للتشغيل المحلي (local-first)

- **التاريخ:** 2026-10-11
- **السياق:** المطلوب أن يعمل النظام على جهاز/شبكة داخلية (XAMPP + MariaDB) بلا وكيل عكسي ولا
  HTTPS. كان نموذج الأمان مبنيًا على لافتراضات استضافة عامة: ترويسة
  `Content-Security-Policy: default-src 'self'` منعت `eval` الذي يستخدمه React في وضع التطوير،
  فسقط تمهير الواجهة وتسجيل الدخول من المتصفح تمامًا (رُصد فعليًا في المتصفح)، كما أن
  `secure` على كوكي الجلسة كان يجعل الكوكي تُرفض تحت `http://localhost`.
- **القرار:** إبقاء الحماية على ما يمنع الأخطاء الحقيقية وإسقاط ما يفترض إنترنت عام:
  - **بلا CSP وبلا HSTS في التطبيق**؛ الترويسات المُرسلة هي X-Frame-Options `DENY`،
    X-Content-Type-Options `nosniff`، Referrer-Policy، Permissions-Policy (`next.config.js`).
  - كوكي `sms_session`: `httpOnly` + `sameSite=lax` دائمًا، و`secure` **فقط** عندما يكون
    `APP_URL` يبدأ بـ `https://` (`src/shared/auth/session.ts`) — فلا تتعطّل الجلسة على localhost.
  - الأسرار بحدّ 32 حرفًا مع فشل مبين عند الإقلاع (`src/shared/config/env.ts`) بلا تدوير قسري
    أو شروط استضافة.
  - الجلسات: `SESSION_IDLE_MINUTES=60` و`SESSION_ABSOLUTE_HOURS=24`؛ قفل brute-force
    `LOGIN_MAX_ATTEMPTS=5` / `LOGIN_LOCKOUT_MINUTES=15`؛ **TOTP معطّل افتراضيًا** (`TOTP_ENABLED=false`)
    ومنفّذ للكود فقط.
  - كلمة مرور المدير الأولى: تغيير إلزامي عند أول دخول (`mustChangePassword=true` من `seed`) —
    بقيت لأنها تحمي الحساب الوحيد في قاعدة محلية قد تكون مشتركة.
- **البدائل:** CSP بـ nonces (يتطلب إعادة كتابة كل سكربت مضمّن ويتعارض مع `eval` في التطوير، ثم
  كسر مماثل عند كل تعديل)، أو تشغيل الوكيل العكسي + شهادة محلية (تعقيد setup يرفضه المستخدم)،
  أو جعل `secure` ثابتًا `false` (يُفقد الحماية عند النشر لاحقًا بدل ربطه بالـ scheme).
- **النتائج:** + الدخول واللوحة والطباعة تعمل في متصفح على `localhost:3000` (✅ مُجرَّب، و66/66
  E2E)، و`npm run test:e2e` بلا أي ضبط أسرار. − **الحماية الآن تعتمد على أن الوصول محلي/داخلي**
  وعلى انعدام السكربتات الخارجية: إن خرج النظام للإنترنت يجب إضافة CSP بـ nonces وHSTS عند
  الوكيل العكسي وتفعيل TOTP قبل ذلك (SECURITY.md §8). عتبات القفل وTOTP لم تُختبر آليًا.

## ADR-16: اختبارات E2E تدخل بحساب `seed:demo` لا بحساب المدير الحقيقي

- **التاريخ:** 2026-10-11
- **السياق:** `tests/e2e/helpers.ts` كان يفرض `SEED_ADMIN_EMAIL/SEED_ADMIN_PASSWORD`، وحساب
  `npm run seed` يولد بـ `mustChangePassword=true`، فكان أول تشغيل للاختبارات يغيّر كلمة مرور
  المدير الذي يدخل منه الإنسان إلى `E2E_PASSWORD`. النتيجة أن الحساب الموثّق في README تعطّل
  بعد تشغيل الاختبارات، وضعنا ذلك في الطريق أثناء الصيانة وفقدنا الدخول الموثّق.
- **القرار:** الافتراضي في `tests/e2e/helpers.ts` هو حساب `npm run seed:demo`
  (`admin@demo.test`، وثابتاه منشوران أصلًا في `scripts/seed-demo.ts`)، و`SEED_ADMIN_*` تبقى
  تجاوزًا اختياريًا. تُعرض القيم الفارغة في `.env` كأنها غير مضبوطة (`?.trim() ||`)، و
  `adminSession` تُرجع الكلمة الصالحة فعليًا لتستعملها اختبارات المتصفح بدل افتراض كلمة ثابتة.
- **البدائل:** حساب مخصص للاختبارات (يستلزم سرًّا في `.env` — وهو ما ترفضه سياسة عدم وضع أسرار
  في الملفات/الأوامر، ولا يمكن إنشاؤه بلا تمرير كلمة مرور)، أو إبقاء الاقتران مع `mustChangePassword`
  موثّقًا فقط (يكسر دخول المستخدم بعد كل تشغيل).
- **النتائج:** + `npm run seed:demo && npm run test:e2e` تعمل بلا إعداد (✅ 66/66 في 2026-10-11)،
  وكلمة مرور مدير الإنسان لم تعد تُستهلك. − الاختبارات تكتب بياناتها في قاعدة تحوي بيانات تجريبية
  يراها المستخدم (يمكن تنظفها بإعادة `db push` فارغة أو بحذف صفوف `@example.test`).
